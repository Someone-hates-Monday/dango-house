# 桌面 AI 娘群居应用实施计划 v0.1

制定日期：2026-10-27。

依据：[需求理解与资料调研](./需求理解与资料调研-2026-10-27.md)。本文件是待执行计划，未开始构建应用；所有验收值均为建议目标，尚无实测结果。

## 1. 本次实施目标

先做一个 Windows 桌面应用：三个有不同性格的 AI 角色住在桌面，通过同一个群聊与用户交流，能接话、争宠、记住共同事件，并与桌面动作同步。

第一版体验优先级：

1. 群聊自然、角色有辨识度。
2. 争宠与关系互动有缘由、不过度打扰。
3. 桌面交互顺手，聊天与动作连贯。
4. 模型接入稳定、设置清楚。
5. 用番茄钟保留轻任务抢单体验。

最终 v0.1 覆盖 OpenAI（对应用户提到的 ChatGPT 方向）、Claude、DeepSeek、Gemini、GLM、Kimi、Grok 七类服务；开发过程中先以一个真实服务完成闭环，再补齐其余适配。没有凭证的服务只能标记为“适配待实测”，不能计入已验证支持。

## 2. 范围和工作假设

### 首版交付

- 可安装的 Windows 应用、托盘入口、统一群聊和透明桌宠窗口。
- 三个原创演示角色，优先采用一套像素精灵风格；角色表现接口允许以后换成 Q 版资源。
- 待机、走动、点击反馈、拖拽、说话、庆祝等基础状态。
- @、广播、选人接话、静音角色、暂停自动对话。
- 表扬、点名、专注完成等关系事件；可调节争宠与亲密互动强度。
- 低频主动关怀、免打扰、专注状态、一键隐藏。
- 本地聊天记录、可查看和修改的用户偏好及角色记忆。
- 七家服务的配置入口、连通测试、流式回复、取消和错误反馈。
- 一个真实番茄钟任务，支持报名、指派、取消与完成反馈。
- 本地角色包导入：初版支持 Character Card V2 核心人物字段和应用自有精灵资源清单，导入时预览缺失内容。

### 后续扩展

语音、Live2D／3D、V3／CHARX 完整兼容、桌面截图理解、自由操作电脑、外部 Agent 连接、角色市场与云同步进入后续版本。

Windows 优先、像素占位资源和三个角色属于实施默认值；不构成用户已确认的最终发行范围或美术方向。首轮使用简单原创资源验证交互，美术精修在体验稳定后进行。

## 3. 技术路线与决策门槛

### 默认路线

建议使用 **Electron + React + TypeScript**，本地结构化数据存入 SQLite，模型调用与数据访问放在后台进程。应用 UI 和桌宠渲染只通过受限 IPC 接收业务事件和发出用户操作。

这是以快速实现 Windows 多窗口与群聊体验为目标的工程选择。正式依赖版本、数据库绑定方式及系统凭证存储方案在项目初始化时核对并锁定。

参考依据：[Electron 窗口交互](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions)。前轮已核对官方资料，仍需本机验证透明窗口的实际行为。

### 第一项技术验证

用同一场景验证自建桌面壳，并限时评估 [Fidget](https://github.com/omesser/fidget) 的相关模块：

- 三角色显示、点击命中、透明区域穿透、拖拽。
- 多显示器和常见缩放比例。
- 点击角色后打开统一群聊、避免非交互动作抢焦点。
- 一键隐藏与全屏场景。

仅当 Fidget 能在不大改其会话和实例模型的情况下承载统一群聊，并明显减少已验证的桌面适配工作时，才考虑以它为底座。否则按默认 Electron 路线推进，参考其设计。评估产物必须包含运行结果和改造清单，不停留在 README 对比。

### 窗口组织

- 一个群聊／设置主窗口。
- 每个显示器一个透明桌宠绘制窗口，统一渲染该屏角色，先避免每个角色独占一个浏览器渲染进程。
- 一个后台业务入口统一管理角色、群聊、计时和数据。
- 桌宠可关闭而群聊仍可使用；关闭主窗口后是否驻留由设置控制。

若透明穿透或多屏成本超过预期，先完成单屏可用版本；多屏通过测试后再标记支持，最终发布说明写清范围。

## 4. 模块与最小接口

接口按体验需要定义，首版保持在同一项目内，不提前拆分服务。

### desktop：桌面表现

接收角色位置、动作和气泡事件，输出点击、拖拽等用户意图。处理边界、缩放、隐藏与输入命中，不负责调用模型或修改关系。

### conversation：群聊与导演

接收用户消息或主动事件，选择发言人、构造上下文、安排回复、控制轮次。维护回合 ID 与取消标记；用户开始新回合后，旧请求的延迟结果不得混入新回合。

建议初始调度规则：@ 优先；普通消息选择一位主答，可安排最多一位补充；只有明确的多人互动场景才允许三人参与。自动闲聊每次最多三条角色消息，结束后进入共享冷却。具体参数通过体验测试调整。

### characters：角色与关系

维护静态角色定义、角色实例状态、用户关系与角色间关系。关系变化来自带 ID 的事件，重复接收同一事件不重复更新。人物卡与用户记忆分别存储。

### providers：模型连接

对外提供统一生成、取消与用量事件；内部保留不同厂商消息格式和能力差异。业务层只依赖“可生成文字、可流式、是否支持结构化输出”等能力，不依赖具体模型名。

每条回复绑定角色 ID；模型只生成该角色的文本和允许的表现建议。动作和表情使用白名单；解析失败时降级为文字加中性动作。内部思考字段不作为角色发言显示。

### memory：本地记录与记忆

聊天记录、用户明确保存的偏好、共享事件和角色个人记忆分别管理。初版先实现“记住这件事”和编辑／删除；自动提炼记忆在可回溯来源和去重验证后启用。

近期消息加摘要组成群聊背景，当前说话者加载完整设定及相关记忆；角色只读取允许共享的内容。每条提炼记忆保留来源消息，修改偏好后同步失效相关旧摘要或记忆。

### activities：主动互动与轻任务

管理打扰预算、冷却、免打扰和番茄钟。任务执行状态与角色报名演出分开；预留后续执行连接接口，首版不实现通用 Agent 调度框架。

## 5. 阶段计划与退出条件

### M0：项目骨架与桌面验证

任务：

- 建立项目、启动脚本、开发说明、类型检查和最小打包路径。
- 完成桌面窗口技术验证和 Fidget 复用决策记录。
- 定义人物、消息、回合、关系事件、任务和服务连接的数据结构。
- 建立离线演示模式与确定性假模型，界面明确标记“演示模式”。

交付：能启动的桌面壳，三个人物占位图，一个可打开的空白群聊，以及技术决策记录。

验收：点击和拖拽有效，透明区域可操作底层窗口；隐藏／恢复可靠；至少完成一次 Windows 安装包启动。空群聊提供清楚的开始入口。

依赖：无 API 凭证也可完成。

### M1：完成可玩的离线共居演示

任务：

- 制作三个角色的性格档案、关系与动作资源清单。
- 实现统一群聊、@、选人、发言队列和桌面气泡同步。
- 用脚本跑通表扬争宠、安静陪伴、点击反馈和三人接话。
- 完成托盘、一键隐藏、角色静音、全局暂停、活动范围设置。

交付：可完整演示核心体验的离线版本。

验收：连续完成“打开桌面—群聊—夸奖一人—其他人反应—恢复安静”流程；三人身份和桌面说话人对应；普通动画不发起模型请求。脚本演示保持明确标识。

依赖：M0。先评审这段体验再扩展美术，降低返工。

### M2：接通真实模型与群聊导演

任务：

- 实现连接设置、凭证引用、真实测试请求与错误说明。
- 以用户提供有效凭证的一家服务接通真实群聊。
- 实现按角色生成、流式输出、打断／取消、回合过期处理和消息持久化。
- 将脚本驱动的人物回复切换为“规则选择说话人＋模型生成内容”。
- 记录调用次数、返回用量和耗时；缺失用量标记未知，不填零。

交付：三角色真实群聊 Alpha。

验收：@、广播、抢话抑制、断网、无效凭证、限流和取消均有明确结果；用户中途发新消息后，旧请求不会继续安排接话。连接测试必须实际生成最小回复，不能仅凭能获取模型列表判定可用。

依赖：M1；真实服务验收需要至少一家可用凭证。凭证通过应用本地设置录入。

### M3：关系、记忆、主动关怀与轻任务

任务：

- 将表扬、点名、被忽略和共同完成任务变成关系事件。
- 加入共享冷却、日常／安静／热闹档位、免打扰与专注状态。
- 实现用户偏好和角色记忆查看、编辑、删除，重启后恢复。
- 实现真实番茄钟、报名与负责人分配、取消和完成反馈。
- 对睡眠／恢复、应用重启和过期计时定义一致行为：恢复后根据持久化的结束时间结算一次，不重新开始倒计时。

交付：能常驻使用的陪伴 Beta。

验收：自动闲聊自行收尾；免打扰时没有主动模型调用或通知；重复事件不叠加关系变化；一次专注请求只创建一个任务；取消后不再发送完成庆祝。模型失败不影响真实计时。

依赖：M2。

### M4：七家适配、角色导入与发布

任务：

- 逐一补齐七家服务的消息、流式、取消、错误与用量映射。
- 区分未配置、已配置、测试成功、调用失败、待实测等状态。
- 允许每个角色选择服务／模型，提供统一默认值；切换时保留人物与记忆。
- 完成人物卡导入预览、精灵资源校验、缺失动作回退与来源记录。
- 执行 Windows 打包、安装、卸载、数据保留选项与升级迁移验证。
- 整理演示素材、操作说明、支持范围和已知问题。

交付：Windows v0.1 安装包、源代码、使用说明、服务适配验证记录。

验收：七家分别通过同一基础场景；没有凭证的项明确保留“待实测”状态并作为发布缺口报告。没有完成七家实测时，可交付预览版，但不宣称七家全部可用。

依赖：M3。供应商接口工作可在 M2 接口稳定后穿插，但不抢占核心体验验证。

## 6. 首版互动内容清单

三个原创占位角色：热情行动派、冷静策划型、嘴硬照顾型。名字和最终外观可后续替换。

每个角色准备：

- 核心动机、说话风格、喜欢与回避的话题。
- 被夸奖、被冷落、别人受关注、失败和任务完成时的反应。
- 与另外两人的关系标签、专属接话示例。
- 一种主动邀约和一种安静陪伴动作。
- 足够覆盖基础事件的表情和短动作，缺失时有回退。

初版至少准备六个可复现的评审场景：初次见面、普通闲聊、@ 单人、表扬争宠、主动休息提醒、专注任务抢单。脚本用作体验基准；真实模型评审允许不同措辞，但应保持人物动机和事件因果。

## 7. 数据、凭证和执行边界

- 凭证放在后台可访问的系统保护存储或经验证的加密存储，不存入角色包、聊天记录或日志。
- 渲染层不直接访问文件系统和模型凭证，IPC 使用明确的方法与参数校验。
- 导入人物卡视为内容，不允许覆盖应用权限；初版不运行角色包脚本。
- 用户可以删除记忆和聊天；删除时同时处理衍生摘要，避免下次又从摘要恢复。
- 默认主动关怀使用计时、应用状态和用户提供的信息；截图感知留待后续明确设计。
- 只有番茄钟等实际实现的能力可以被执行；模型输出的“我去做了”不会自动变成任务成功。

这些要求直接影响产品行为，应随相关模块实现，无需另建复杂权限平台。

## 8. 验证方式

### 自动化验证

集中测试会造成真实错误的逻辑：导演轮次与取消、过期请求、免打扰、事件去重、人物与记忆归属、任务只创建一次、重启后的计时恢复、供应商流式解析和数据库迁移。

使用确定性假模型和经过脱敏的响应样本测试边界；真实请求另行记录，不能以样本通过代替真实服务验收。

### Windows 人工验证

检查透明命中、拖拽、群聊焦点、缩放、屏幕边界、全屏、托盘、隐藏与安装卸载。多屏需有实际设备或可用测试环境验证。

### 体验评审

把六个基准场景在真实模型下各运行多轮，记录身份混淆、重复发言、争宠是否生硬、主动关怀是否打扰、取消是否及时。先根据本地试用结果修正，再邀请少量目标用户试用。

建议初始参数：普通回合最多两位发言；多人互动最多三位；单次主动闲聊最多三条；所有角色共用冷却和预算。参数可调整，不将数值本身当作体验达标证据。

### 性能和用量

在同一台记录过配置的设备测量三角色待机、群聊生成、免打扰三个状态的 CPU、内存及请求数。首轮建立基线后再确定资源目标，避免在没有实测时承诺具体内存上限。

## 9. 工作量与推进方式

按一名熟悉 TypeScript 桌面应用的开发者、使用占位美术、及时获得模型凭证估算，首个完整预览版可按 **约 3—5 周工作量**安排。此为粗估，不是交付日期承诺；正式美术、模型适配差异和 Windows 窗口兼容可能增加工作量。

推进顺序为 **M0 → M1 → M2 → M3 → M4**。每阶段留下可运行产物、通过与未通过的验收项、已知问题。先在 M1 评审是否有趣，再在 M2 评审真实群聊是否自然。

影响后续阶段但不阻塞 M0／M1 的输入：

- 真实模型测试所需的本地 API 配置。
- 最终选用像素风还是 Q 版，以及正式角色资源。
- 计划支持的 Windows 版本与可用多屏测试环境。

## 10. 开工批次

下一次进入实施时，首批完成 M0 和 M1 的最小路径：

1. 初始化项目并锁定依赖，补充启动／打包说明。
2. 建立主窗口与透明桌宠窗口。
3. 放入三个原创占位角色，打通点击、拖拽和统一群聊。
4. 建立回合与事件协议，用演示模式跑通一段争宠互动。
5. 输出实际运行结果、桌面验证记录和下一批任务。

首批成功标准是“一段可以亲手玩的三角色共居体验”，随后接入真实模型并逐步达到完整 v0.1。
