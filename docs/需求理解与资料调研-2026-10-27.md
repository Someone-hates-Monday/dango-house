# 桌面 AI 娘群居应用：需求理解与首轮资料调研

调研日期：2026-10-27。阶段：产品探索，尚未实现应用或验证 API 连通性。

## 1. 已确认的方向

用户希望多个有角色设定、鲜明性格的 AI 娘以 Q 版或像素形态共同生活在桌面；通过一个统一群聊与用户交谈，也彼此互动。收到任务时会抢着接，空闲时会关心用户、聊天、争宠。长期希望联动用户已有模型 API 和 Agent 应用，兼顾娱乐和实用。

本轮追问后，用户明确：**第一版先做好群聊、争宠和桌面互动**。首批希望覆盖的模型服务包括 **ChatGPT、Claude、DeepSeek、Gemini、GLM、Kimi、Grok**。

尚未确定：最终发行平台、Q 版或像素风的主风格、原创或二创角色、是否需要语音、商业化方式、用户现有的 API 凭证与 Agent 应用。下文按 Windows 优先、文字优先、可导入角色包提出建议；这些是工作假设。

## 2. 产品理解

建议定位为：**一个住着多位 AI 角色的桌面小世界，群聊是它们与用户共同生活的主入口。**

“后宫”在这里对应的是可调节的亲密互动、角色间的关系与争宠演出。产品的持续吸引力需要来自每个人物的差异、共同经历、对用户的记忆以及桌面上的存在感。

角色不必各自对应一家模型。需要把四件事分开：

- 角色是谁：设定、口吻、偏好、与其他角色的关系。
- 角色长什么样：立绘、精灵图、动作、表情、声音。
- 角色用什么思考：可选择的模型服务与参数。
- 角色能做什么：后续授权连接的工具和 Agent。

这使得三个角色可以共用一个模型，也可以分别使用不同服务；更换模型时，角色档案与本地记忆仍可保留，但性格表达效果需要重新评估。

## 3. 核心体验和需求

### 3.1 桌面共居

建议初版同时展示三个角色，以便观察双边和三角关系。这是原型规模建议，不是最终人数限制。

- 待机、走动、坐下、拖拽、被点击、说话、庆祝等基础动作。
- 点击任一角色打开同一个群聊，并可预选 @ 该角色。
- 角色对话时，桌面同步展示说话人、表情或短气泡。
- 允许角色靠近、围观、互相招呼；初版用预定义事件和动作组合实现。
- 桌面活动范围、大小、置顶、透明区域穿透、一键隐藏、托盘入口。
- 全屏、专注、免打扰时减少或暂停活动，避免抢走输入焦点。
- 断网或没有模型配置时仍可走动和响应触摸；清楚显示聊天不可用。

Q 版与像素风是两种表现资源，不必在第一版同时制作两套。建议先用一套风格完成端到端体验，再通过角色资源接口支持另一套。

### 3.2 统一群聊

- 群内有用户、多个角色和少量系统状态消息，明确区分身份。
- 支持广播、@ 指定角色、暂停自动对话、暂时静音某个成员。
- 用户一句话不要求所有角色逐一回答；根据被提及、话题相关性、关系和近期发言选择说话人。
- 支持角色接话、吐槽、附和、争宠以及共同回忆，避免所有人轮流复述同一个观点。
- 群聊可回看；角色发出的主动气泡也写入群聊，保证桌面与聊天记录一致。
- 用户输入时暂停安排新的闲聊轮次；已开始的输出提供取消或让位机制。

### 3.3 争宠与关系

建议将关系机制做成“事件驱动的演出”：被表扬、被点名、一起完成小任务、用户长时间未互动，会影响下一次谁主动发言和如何发言。

- 初版只需少量状态：对用户的熟悉度、短期心情、对其他角色的关系标签、最近受关注程度。
- 用共同事件解释变化，而不是每发一句话就机械增加好感度。
- 亲密程度、争宠强度、主动频率可调；允许只保留朋友式陪伴。
- 争宠宜表现为邀约、撒娇、轻微吐槽和合作竞争；避免反复责备用户没陪伴或逼迫用户表态。
- 每个角色至少有一种与其他角色的专属互动和一种安静陪伴方式。

原创占位角色示意：热情行动派会先举手，冷静策划型会补充细节，嘴硬照顾型用吐槽提醒休息。人格应体现在行动和交流策略上，而不只依靠口癖。

### 3.4 主动关怀

第一版用定时、用户主动提供的信息、应用空闲状态等有限事件触发。提醒休息、喝水是陪伴功能；没有传感器或用户输入时，不把久坐、失眠等推断当作已知健康事实。

建议提供安静、日常、热闹三档；所有角色共用一个打扰预算和冷却时间。全屏、免打扰、刚被用户忽略时抑制触发。日常动画与大多数事件无需调用大模型。

### 3.5 抢着做任务

第一版可用番茄钟、待办、简单文本协助等轻任务验证“抢着做”的体验。

例：用户说“陪我专注二十五分钟”。行动派先报名，策划型安排计时，照顾型承诺结束时提醒休息；只有一个计时任务被创建，其他角色用陪伴动作参与。

**报名发言与执行权限分离。** 多人可以表示愿意，任务由调度器指派负责人。后续真正接入 Agent 时，每个任务具备独立 ID、执行状态与结果凭据；遇到超时需先确认外部状态再决定重试，避免重复写入。

角色可以用自己的口吻汇报，但“完成”必须来自计时器、工具或 Agent 的实际结果。初版没有的执行能力应明确显示为暂未连接。

## 4. 已查到的相邻项目

以下能力来自官方文档或项目 README 的声明，未在本机安装和实测。未在文档确认某能力，不等于该项目没有这项能力。

### Fidget：优先研究的近邻

文档描述了桌面角色、性格包、模型 API，以及通过 ACP 连接 Agent、通过 MCP 回调角色动作。采用 Rust／Tauri，MIT 许可。它与“桌宠成为已有 Agent 的形象入口”非常接近。可借鉴角色、行为与执行端分离的设计；统一多人群聊和关系演出是否现成可复用，仍需源码与运行验证。[项目资料](https://github.com/omesser/fidget)

### AIRI：虚拟角色与多模态参考

项目提供桌面版本，支持 Live2D／VRM、语音及多种模型来源，仓库标注 MIT。适合研究角色表现与模型连接。它的目标和组件较多，是否直接作为本项目底座，需要评估接入和裁剪成本。[项目资料](https://github.com/moeru-ai/airi)

### SillyTavern：群聊机制与角色生态参考

官方群聊文档有点名、话多程度、不同发言顺序及切换角色卡等机制。它说明群聊需要明确的说话人选择策略；可以参考其交互，并兼容角色卡，桌面共居与任务状态仍需本项目设计。[群聊文档](https://docs.sillytavern.app/usage/core-concepts/groupchats/)

### Open-LLM-VTuber：语音和桌宠模式参考

文档声明提供 Live2D、透明置顶桌宠模式、主动说话及多种语音和模型后端。README 同时说明正在规划 v2，并提示长期记忆功能暂时移除；不能将聊天日志持久化直接当作长期记忆已完成。适合后续语音阶段研究。[项目资料](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)

### VPet：桌面动作与创作生态参考

支持互动、动画、创意工坊和代码插件，可嵌入 WPF 应用。代码采用 Apache-2.0；自带动画有单独授权说明。可参考动作系统与创作工具，是否做成其插件取决于是否优先 Windows／WPF 与现有社区。[项目资料与动画授权](https://github.com/LorisYounger/VPet)

**本轮判断：** 已有项目覆盖了不少组成部分，尤其 Fidget 已接近“桌宠 + Agent”。本项目值得验证的组合是“多角色共居 + 统一群聊 + 可持续的关系互动”。这只是首轮定位判断，不是市场空白或用户需求已被验证的结论。

## 5. 七类模型服务的接入理解

第一版建议采用用户自行配置 API Key 的连接方式。网页聊天产品、开发者 API、Agent 客户端是不同接入对象；接通模型 API 不会自动获得网页中的历史对话、记忆、插件或订阅权益。各账号是否可调用、可用区域与费用，需要在实现时按服务官方规则确认。

- **ChatGPT 方向：** 产品接入项宜标注 OpenAI，使用官方 API；OpenAI Docs 的快速开始展示 API Key 与 Responses 调用。本轮使用 OpenAI Docs 技能核对这一区别。[官方快速开始](https://developers.openai.com/api/docs/quickstart)
- **Claude：** 建议独立 Messages 适配器，处理其消息与流式事件格式。[官方 API 概览](https://platform.claude.com/docs/en/api/overview)
- **DeepSeek：** 官方声明兼容 OpenAI／Anthropic 格式，可作为通用适配器候选。[官方接入说明](https://api-docs.deepseek.com/quick_start/agent_integrations/)
- **Gemini：** 有原生 API 与 OpenAI 兼容方式。文字原型可评估兼容入口，高级功能按能力差异处理。[官方兼容说明](https://ai.google.dev/gemini-api/docs/openai)
- **GLM：** 智谱提供 OpenAI 兼容文档，通用 API 与特定套餐入口需分别核对。[官方兼容说明](https://docs.bigmodel.cn/cn/guide/develop/openai/introduction)
- **Kimi：** 有官方 API Key 与调用快速开始，接入时使用对应平台和模型配置。[官方快速开始](https://platform.kimi.com/docs/get-api-key)
- **Grok：** 有官方开发者 API，具体调用能力按模型与端点验证。[官方开发文档](https://docs.x.ai/overview)

上述是文档层面的接入可行性，**尚未测试任一供应商的实际请求**。不在需求阶段硬编码“最新模型”或价格；保存服务、端点、模型 ID、流式与结构化输出能力。模型列表获取失败时应允许手工配置。

建议首轮用一个用户实际拥有凭证的服务跑通核心体验，同时设计适配器边界；随后把其余六个接入项逐一验证。七家都希望覆盖，不意味着角色数量或第一轮原型必须达到七个。

## 6. 角色包与二创设定

Character Card V2 已定义姓名、性格、情境和示例对话等字段；V3 进一步描述资源与打包方式。建议兼容导入而不重新发明整套人物描述格式。[V2 规范](https://github.com/malfoyslastname/character-card-spec-v2)；[V3 规范](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)

角色卡不能保证附带可用的桌宠动作。建议资源包拆为：人物卡、精灵图与动作映射、可选音色、来源与授权说明。关系、当前心情和用户记忆存为本地实例状态，避免导出人物卡时把用户隐私一起打包。

导入的世界观与人物文字属于内容数据，不能改变应用的工具权限或执行策略；初版不执行角色包中的脚本。导入后先预览字段和缺失资源。

二创设定丰富能降低创作门槛，但“网上找得到”不能作为允许随应用分发的依据。默认演示包建议用原创或有明确授权的内容，社区包保留来源和许可字段。代码与素材授权须分开核对；VPet 动画、Open-LLM-VTuber 的 Live2D 示例均有独立说明。[VPet 说明](https://github.com/LorisYounger/VPet#动画版权声明与授权)；[Live2D 示例说明](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber#live2d-sample-models-notice)

## 7. 建议的系统划分

以下为设计建议，尚未选定技术栈。

1. **桌面表现层：** 显示多个角色、执行动作、处理点击拖拽与穿透。
2. **群聊导演：** 判断话题、选择说话人、安排接话、限制自发对话轮数。
3. **人物与关系：** 静态设定、用户偏好、关系事件、可编辑记忆。
4. **模型连接层：** 七家服务适配、流式输出、失败反馈与用量记录。
5. **事件与轻任务：** 休息提醒、番茄钟、待办，以及真实任务状态。
6. **后续执行连接层：** MCP 工具、ACP Agent、厂商 SDK／CLI 及可选 A2A。

第一版可让群聊导演先用规则选人，再为被选中的角色分别生成回复。角色之间共用近期群聊摘要，只加载当前说话者的完整设定及相关记忆。这样更容易保持身份，也避免每条消息都让所有角色各调用一次模型。

单模型一次生成多人对话可作为节省开销的对照方案，但需要检验身份混淆、抢话和重复；不能仅凭调用次数少就判定体验更好。

桌宠动作由本地状态机持续运行，大模型只在用户消息或少量事件时参与。关系状态在明确事件后更新，动画不直接驱动“感情数值”。

### 应用还是插件

当前倾向先做独立桌面应用：它更适合统一群聊、多角色关系与多供应商连接；可保留连接现有 Agent 的扩展接口。

若最终以 VPet 创意工坊用户为主要对象，插件路线值得单独评估；若主要为某款开发工具提供陪伴，可做该工具连接器。当前用户目标跨多个服务，尚不适合把体验绑定在单一聊天客户端内。

### Electron 与 Tauri

两者官方资料都支持桌面窗口定制；Electron 有明确的鼠标穿透 API，Tauri 支持透明窗口。[Electron 窗口交互](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions)；[Tauri 窗口定制](https://v2.tauri.app/learn/window-customization/)

如果目标是快速验证 Windows 群聊与桌面交互，可优先评估 Electron／TypeScript。若团队熟悉 Rust，并把安装包和常驻开销放在前面，可评估 Tauri。透明窗口、多屏缩放、输入焦点和全屏行为需要做同一场景原型再决定；当前没有性能实测依据。

## 8. 后续 Agent 联动边界

- **模型 API：** 提供生成回复等能力，不自动代表一个可执行任务的 Agent。
- **MCP：** 连接工具、资源与外部系统，适合文件、搜索、待办等能力。[官方说明](https://modelcontextprotocol.io/docs/getting-started/intro)
- **ACP（Agent Client Protocol）：** 面向编辑器／客户端与编码 Agent 的通信，可研究会话、进度与取消；须核对目标 Agent 的实现或适配器。[官方说明](https://agentclientprotocol.com/get-started/introduction)
- **A2A：** 面向实现该协议的 Agent 间任务协作，作为后续选项。[官方说明](https://a2a-protocol.org/latest/)
- **专用 SDK／CLI：** 例如 Claude Code 有官方程序化运行说明，但该能力与 Claude 网页聊天不是同一个接口。[官方说明](https://code.claude.com/docs/en/headless)

“用户已经在使用某应用”不足以判断能否控制它。连接器必须列出可用能力、权限、运行状态与结果回传方式；会话恢复和现有记忆共享也应逐项验证。本轮不承诺自动接管七家产品的网页会话。

## 9. 第一版范围与验证

### 建议纳入

- 三个可辨认的角色、一套桌面视觉风格、统一群聊。
- @、自动选人、有限接话、可暂停的角色间闲聊。
- 点击、拖拽、走动、说话与事件表情联动。
- 少量关系事件与可调争宠强度。
- 可编辑的用户偏好、角色记忆及群聊记录。
- API 配置与连通测试；最终覆盖用户列出的七家，按适配完成度明确标注。
- 免打扰、全局闲聊预算、一键隐藏。
- 一个真实轻任务闭环，例如番茄钟，并支持取消。

### 后续阶段

语音与口型、复杂 Live2D／3D、自由桌面视觉感知、开放脚本插件、外部 Agent 执行、角色市场、跨设备同步。第一版保留“抢单”演出，但不必先实现多 Agent 工作系统。

### 首轮验收场景

以下是建议测试标准，非实测结果。

1. 三个角色围绕同一话题接话，用户能区分谁是谁，且不会连续复述。
2. @ 一位角色时她先回应，其他成员能适度参与；用户可完全关闭插话。
3. 用户夸奖其中一位，另一位产生符合关系的反应，同时桌面动作同步。
4. 无输入的一段时间内，角色按设定交流并自行收尾，不形成无上限互相触发。
5. 进入免打扰后不主动打断；断网后基础桌宠动作继续。
6. 同一句番茄钟请求只创建一个任务，结束时由真实计时事件触发汇报。
7. 更换模型后档案仍在，流式中断或服务错误不会让角色冒称已经完成回复或任务。

### 需要收集的数据

先观察用户是否愿意常驻、是否主动打开群聊、能否区分角色、主动关怀被接受还是关闭。技术侧记录每回合调用数、实际输入输出用量、首字延迟、重复发言率、常驻 CPU／内存及断线恢复。

成本按实际调用计算：各次请求的输入 token × 输入单价 + 输出 token × 输出单价，再加后续语音等费用。具体价格、重试成本与供应商差异在选定账号和模型后核算；本轮没有月费估算依据。

## 10. 下一阶段最值得验证的问题

首先做三角色的一段完整共居演示：打开桌面、进入群聊、夸奖其中一人触发争宠、收到休息提醒、创建并结束一个专注任务。它能直接检验角色是否有辨识度、关系是否自然、桌面与聊天是否连贯。

再比较两种底座：阅读并试跑 Fidget 的最小相关路径，与自建桌面壳＋群聊导演原型。决定依据是满足本项目体验所需的改造量、可维护性与实际资源占用，不能仅凭 README 宣称。

本轮已完成需求梳理、官方资料核对及第一版边界建议；尚未进行用户访谈、市场规模研究、竞品实机比较、API 调用测试或最终技术选型。
